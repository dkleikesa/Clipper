# Code Commit

用 Conventional Commits 1.0.0 写提交信息并完成提交流程。标题说**做了什么**，正文说**为什么**。

## 1. 格式

```
<type>[(scope)][!]: <描述>

正文
```

| 字段 | 必填 | 规则                                                   |
| --- | --- |------------------------------------------------------|
| `type` | 是 | §2 表里的词，小写；后接半角 `: `（冒号 + 一个空格）                      |
| `scope` | 否 | 英文小写名词，全仓库同一套词（`driver` / `cli` / `history`）；横跨整库时省略 |
| `!` | 否 | 标记破坏性变更：在描述前加 `!`，并在正文说明影响与迁移方式                      |
| 描述 | 是 | 简要概括“本次变更做了什么”， ≤ 30 个字 、陈述句、不加句号                    |
| 正文 | 否 | 说明“变更的背景原因与实现逻辑”，排版上与标题空一行，单行不超过 30 字且段落间用空行分隔      |

- 正文按 30 字断行：汉字占两列，一行因此最多 60 列；`git log` 的正文再缩进 4 格，80 列终端里放得下。半角词按 1 字计，只会更窄。
- 断行时不要把 `「…」` 这类短引语与半角词拆开：引语整段挪到下一行，半角词不到万不得已不拆。

## 2. type

| type | 用在 | 别用在 |
| --- | --- | --- |
| `feat` | 用户能感知的新能力 | `chore` |
| `fix` | 行为错了，改对 | `refactor` |
| `refactor` | 行为不变，只是结构更顺 | `fix` |
| `test` | 只动测试 | `fix` |
| `style` | 只动空格 / 换行 / import 顺序 | `refactor` |
| `perf` | 性能优化 | `refactor` |
| `docs` | 只动文档 / 注释 | `feat` |
| `build` | 构建系统、依赖 | `chore` |
| `ci` | CI 配置与脚本 | `chore` |
| `chore` | 版本号、脚手架、仓库配置、发布 | `feat` |
| `revert` | 回滚既有提交 | — |

- 选不出唯一 type，说明该拆；既加功能又修 bug、且互相依赖拆不开时，选影响更大的那类，并在正文说明。

## 3. 流程

1. 看改动：`git --no-pager status --short`、`git --no-pager diff`，弄清哪些文件属于同一件事。
2. 拆分：一个提交只做一件事；同一文件混着两件事、又没法用 `git add -p` 干净拆开时，**合成一个**，别造出单独检出后不可用的中间提交（例如改了调用方却没改被调用方）。
3. 暂存：`git add <具体文件>`，不要 `git add -A`。
4. 提交：多段用多个 `-m`（第二个 `-m` 起各自成段）；写完对照 §1、§2 各表过一遍。
5. 收尾：只报结果——hash + 标题；几个改动合成过提交就说一句为什么。

## 4. 禁止

- 未经明确要求：不 push、不 amend、不 reset、不 `--no-verify`。
- 不带无关文件与构建产物。
- 不写过程话（「按用户要求」「本次会话」）与生成器署名。
